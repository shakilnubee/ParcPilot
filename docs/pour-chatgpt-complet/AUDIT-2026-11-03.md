## 1. Concurrence des données

**Mécanique vérifiée** `[CONFIRMÉ]` : écriture des **réglages** via `FP.settings._pushSettings` (app.js:6635) = **lecture serveur fraîche → fusion « delta » → upsert**, sérialisée **par onglet** (`_serialize`, app.js:6620, file par `id`, pas entre appareils). Les **COLLECTION_KEYS** (app.js:6700, ~90 maps de données) sont fusionnées **entrée par entrée** (`mergeMap/mergeArr`) ; `applyDelta` (app.js:6774) ne traite **que les clés présentes dans le cache local** → une clé absente n'est jamais supprimée. File **optimiste** `FP.persist` (app.js:13250) : item enfilé **avant** le réseau, flush sur `online`/`pagehide`. Tables de données : `FP.db.update` = **patch partiel** (`.update(champs).eq(pk,id)`, supabase-client.js:354).

### F1 — `app_settings` : pas de CAS `rev` (clés de config) — Élevé — CONFIRMÉ
1. **Problème** : entre le `select('data')` (app.js:6674) et l'`upsert`, aucune vérification de version (`rev` non comparé). Pour une clé de **config non-collection** (`profil`, `societe`, `groupes`, `navOrder`, `sidebarLabels`, couleurs…), deux admins qui modifient **la même clé** quasi simultanément depuis 2 appareils → le 2ᵉ `upsert` écrase la valeur du 1er pour cette clé (dernier gagne).
2. **Gravité** : Élevé (données de config ; rare mais silencieux).
3. **Statut** : CONFIRMÉ.
4. **Fichiers** : `assets/js/app.js`.
5. **Fonctions** : `FP.settings._pushSettings`, `_serialize`, `FP._fusion.applyDelta`.
6. **Tables** : `app_settings`.
7. **Conséquences** : perte silencieuse d'une modif de config concurrente (pas de doublon, pas de resurrection).
8. **Protections existantes** : fusion delta (ne touche que les clés changées), `_serialize` par onglet, `gapfill` sans snapshot, anti-vidage (`trg_01`), snapshots `app_settings_history`. Les **collections** sont fusionnées finement → **non concernées**.
9. **Correction recommandée** : CAS optimiste `rev` (lire `rev` → `update … where id=? and rev=?` → si 0 ligne, relire/refusionner/retenter) — **phase 2 déjà prévue**. Ne jamais écraser en silence : en cas d'échec CAS, refusionner.
10. **Risques de régression** : toucher au cœur anti-perte ; tests de fusion existants à ne pas casser.
11. **Tests** : `tests/unit/fusion-reglages.mjs` + nouveau test CAS (2 écritures concurrentes simulées) ; staging 2 comptes.
12. **Priorité** : Phase 2 (haute).

### F2 — Tables de données : même champ édité en même temps — Moyen — CONFIRMÉ
1. **Problème** : `FP.db.update` patche **seulement les champs passés** → 2 gestionnaires sur **champs différents** du même véhicule = OK ; sur **le même champ** = dernier gagne, sans détection ni avertissement.
2–6. Gravité Moyen · CONFIRMÉ · `supabase-client.js` (`update`), `app.js` (`FP.persist.update`), pages (`commitVehField`…) · pas de table de verrou.
7. **Conséquences** : perte silencieuse d'une saisie sur le même champ (rare).
8. **Protections** : patch par champ (limite fortement la casse) ; édition inline champ par champ.
9. **Reco** : optionnel — CAS par ligne (colonne `updated_at`/`rev`) pour les éditions sensibles ; a minima, re-render sur `fp:data-ready` montre vite la valeur gagnante.
10–12. Régression faible · tests staging 2 comptes · Priorité Phase 2 (moyenne).

### F3 — RPC « remplacer » par entité — Moyen — CONFIRMÉ
1. **Problème** : `fp_conges_remplacer`/`fp_affectations_remplacer`/`fp_contrat_lld_enregistrer`/`fp_forfait_leasing_enregistrer` **remplacent** l'entité ciblée. Deux appareils modifiant **la même** entité (même conducteur/véhicule/contrat) → dernier remplace.
8. **Protections** : verrou **advisory** par conducteur (congés), **validation dates/km avant effacement** (affectations), écriture via file durable. Périmètre = 1 entité à la fois (pas la collection entière).
9. **Reco** : accepter (risque faible, périmètre étroit) ou ajouter un garde `updated_at` par entité. 3. CONFIRMÉ · 12. Phase 2 (basse).

### F4 — `rev` non exploité — Faible — CONFIRMÉ
Trigger `trg_app_settings_touch` incrémente `rev`, mais le code ne le lit jamais → base posée pour le CAS (F1) mais **phase 2 non branchée**. `[DOC: MIGRATIONS-EN-ATTENTE.md]`.

## 2. Autorisations multi-sociétés

### F6 — Config `app_settings` modifiable par un gestionnaire via l'API — Élevé — CONFIRMÉ (garde base NON VÉRIFIABLE)
1. **Problème** : la policy RLS `tenant_app_settings` = `fp_is_admin() OR id = fp_societe()` **autorise un gestionnaire** à écrire la ligne `app_settings` de **sa** société (le rôle `gestionnaire` n'est pas distingué au niveau base). La config réservée à l'admin (profil société, e-mails, groupes, navOrder…) n'est protégée que **côté interface** (`gateParamForGestionnaire`, `parametres.html:2762`). Un gestionnaire techniquement averti pourrait écrire ces clés via l'API Supabase.
2. Élevé · 3. CONFIRMÉ (code) ; l'éventuel garde base `trg_guard_app_settings_config` (`gestionnaire-config-guard.sql`) est **[NON VÉRIFIABLE SANS ACCÈS BASE]**.
4–6. `parametres.html` (gate UI), `multi-societe-rls.sql`/`gestionnaire-app-settings-fix.sql` (RLS) · RLS `tenant_app_settings` · table `app_settings`.
7. **Conséquences** : un gestionnaire pourrait altérer la config de **sa** société (jamais une autre — l'isolation société tient). Pas de fuite inter-sociétés.
8. **Protections** : masquage UI complet ; durcissement RLS **annulé** car il cassait les opérations (la ligne mêle config **et** données de travail).
9. **Correction recommandée** (demandée) : **séparer** config administrative et données opérationnelles en **lignes `app_settings` distinctes** (ou une table config dédiée), puis reprotéger la **config** côté base (RLS `fp_role() in ('ceo','admin')`) **tout en laissant** les données de travail modifiables par le gestionnaire → ne casse pas ses opérations. Refactor de `FP.settings`. **À faire sur demande explicite.**
10. **Régression** : élevée si mal séparé (cœur réglages) → staging obligatoire.
11. **Tests** : staging, compte gestionnaire, tenter écriture config via API (doit échouer) + opérations normales (doivent marcher) ; `isolation.yml`.
12. **Priorité** : Phase 1 (haute).

### F7 — RLS `scans` sans `coalesce('PXP')` — Moyen — CONFIRMÉ
Policy `tenant_scans` = `fp_is_admin() OR societe = fp_societe()` (sans `coalesce(…, 'PXP')`, contrairement aux autres tables, `scans-table-setup.sql`) → une ligne `societe` NULL serait **invisible** aux non-CEO (pas une fuite, une sur-restriction). Reco : uniformiser si des lignes NULL peuvent exister. Priorité Phase 1 (basse, à confirmer en base qu'il existe des NULL).

### F8 — Isolation (reste) — Info — CONFIRMÉ (protégé)
RLS `tenant_*` sur toutes les tables de données (filtrage **en base**) ; storage cloisonné `societes/<slug>/` (`fp_storage_acces`) ; `profiles` sans policy d'écriture (anti-escalade — seul `manage-users` écrit) ; QR via RPC `vehicule_public_par_plaque` (pas de listing du parc) ; **statistiques/exports** lisent `FP_DATA` déjà filtré par société ; **caches** suffixés par société ; Edge publiques scoped par **token**. → **Aucune fuite inter-sociétés confirmée dans le code.**

### F9 — État réel des policies/triggers — NON VÉRIFIABLE
Quelle policy RLS `app_settings` est active, quels triggers sont installés (surtout `trg_guard_app_settings_config`). **Contrôle** : `select policyname, qual from pg_policies where tablename='app_settings';` et `select tgname from pg_trigger where tgrelid='app_settings'::regclass;`

## 4. Portail QR code (conducteurs, sans compte)

### F13 — Sécurité des tokens — Info — CONFIRMÉ (protégé)
`km-collect` (`verify_jwt=false`) résout **token/QR → véhicule → société** côté serveur (service_role) ; **QR désactivé si véhicule hors flotte** ; renvoie des données **non-PII** ; `Cache-Control:no-store`. Un **token invalide/manipulé** ne donne aucun accès (lookup échoue). Un QR ne permet pas de voir un **autre véhicule/société** (scopé par le token). → **Aucune faille confirmée.** (Points 1, 2, 3 de ta liste = ✅.)

### F14 — Double déclaration (double-clic / renvoi) — Moyen — CONFIRMÉ
1. **Problème** : le bouton « Envoyer la déclaration » est **désactivé côté client** pendant l'envoi (`v.html` : `$('sin-send').disabled=true`) → protège du double-clic. Mais **aucune idempotence côté serveur** : `km-collect` insère dans `declarations_conducteur` sans clé anti-rejeu → un **renvoi réseau** (mobile instable, retry) pourrait créer un **doublon** de déclaration.
4–6. `v.html`, `supabase/functions/km-collect/index.ts` · table `declarations_conducteur`.
7. **Conséquences** : doublon de déclaration (le gestionnaire voit 2 cartes) ; pas de perte.
8. **Protections** : bouton désactivé (client) ; messages honnêtes (`photos_partial`).
9. **Reco** : clé d'idempotence côté `km-collect` (hash véhicule+type+description+fenêtre temporelle, ou id généré client renvoyé) → upsert anti-rejeu. (Point 4 de ta liste.)
10–12. Régression faible · test staging (double POST) · Priorité Phase 3.
