## 1. Concurrence des données

**Mécanique vérifiée** `[CONFIRMÉ]` : écriture des **réglages** via `FP.settings._pushSettings` (app.js:6635) = **lecture serveur fraîche → fusion « delta » → upsert**, sérialisée **par onglet** (`_serialize`, app.js:6620, file par `id`, pas entre appareils). Les **COLLECTION_KEYS** (app.js:6700, ~90 maps de données) sont fusionnées **entrée par entrée** (`mergeMap/mergeArr`) ; `applyDelta` (app.js:6774) ne traite **que les clés présentes dans le cache local** → une clé absente n'est jamais supprimée. File **optimiste** `FP.persist` (app.js:13250) : item enfilé **avant** le réseau, flush sur `online`/`pagehide`. ### F1 — `app_settings` : CAS `rev` (clés de config) — Élevé — ✅ RÉSOLU (03/11/2026)
> ⚠️ **Rectificatif (03/11/2026)** : le constat initial ci-dessous visait le `select('data')` de app.js:**6674**, qui est la branche **additive « gapfill »** (1er push / cache vide : le serveur gagne sur les feuilles existantes → **aucun écrasement possible**). Le **chemin normal** d'enregistrement (base serveur connue) est plus bas (app.js:**~6864-6894**) et faisait **déjà** le CAS : `select('data, rev')` → `update … .eq('rev', rev).select('id')` → si 0 ligne, relecture/refusion/retente (4 essais), puis repli sûr par fusion. La seule pièce manquante était la **colonne `rev` en production** : sans elle, `remoteRev` était `null` → repli par fusion `applyDelta` (sûr, jamais d'écrasement brut). **Depuis l'application du socle `20261103130000` en prod (03/11), `rev` existe → le CAS est actif.** Scénario « 2 admins, même clé de config » = désormais **protégé** (le 2ᵉ relit et refusionne au lieu d'écraser).
1. **Problème (historique)** : perçu comme « pas de vérification de version entre lecture et écriture » pour une clé de **config non-collection** (`profil`, `societe`, `groupes`, `navOrder`, `sidebarLabels`, couleurs…). En réalité le CAS existait côté code mais était **dormant** faute de colonne `rev` en prod.
2. **Gravité** : Élevé (config ; rare mais silencieux) — **neutralisé**.
3. **Statut** : ✅ RÉSOLU (socle en prod + code CAS feature-detecting désormais actif).
4. **Fichiers** : `assets/js/app.js` ; migration `supabase/migrations/20261103130000_app_settings_concurrence_rev.sql`.
5. **Fonctions** : `FP.settings._pushSettings` (boucle CAS), `_serialize`, `FP._fusion.applyDelta`.
6. **Tables** : `app_settings` (colonnes `rev` + `updated_at`, trigger `trg_app_settings_touch`).
7. **Conséquences (avant)** : perte silencieuse d'une modif de config concurrente — **ne peut plus se produire** (CAS + refusion).
8. **Protections** : CAS `rev` (actif) + fusion delta + `_serialize` par onglet + anti-vidage (`trg_01`) + snapshots `app_settings_history`. Les **collections** étaient déjà fusionnées finement.
9. **Correction appliquée** : socle `rev` (PR #1196, prod 03/11) + CAS côté code (déjà livré #1121, feature-detecting avec repli fusion si `rev` absent).
